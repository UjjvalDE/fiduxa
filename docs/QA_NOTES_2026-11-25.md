## 3. Issues found and fixed

1. **Customers could see the cleaner's pay and Fiduxa's commission.**
   - Cause: the customer booking detail and list sent the internal `workerPayout` data (amount, commission %, commission €).
   - Fix: these fields are no longer sent to customers. The customer pages never used them.
2. **The invoice line did not include approved extra time.**
   - Cause: after the customer approved extra time, the duration and total went up, but the labour amount the invoice line uses did not. The PDF showed "2.5 h × 25.00 = 50.00" with a total of 62.50.
   - Fix: approved extra time now also raises the labour amount.
3. **"Pay gift card" failed if retried within a minute.**
   - Cause: PayPal returns the same order for a quick retry, and saving it again broke a uniqueness rule. The user saw "A record with this value already exists".
   - Fix: the existing order is reused, the same way booking payments already work.
4. **The Settings / Richtlinien page could not be saved at all.**
   - Cause: the invoice email defaulted to the mail sender setting, which is written as `Fiduxa <service.fiduxa@gmail.com>`. The settings form only accepts a plain address. The same text also appeared on every invoice ("Email: Fiduxa <…>").
   - Fix: only the plain address is used now. Saving works, and the 20 % fee and payout day 5 stay unchanged.
5. **Requests could hang for minutes when the mail server was slow.**
   - Cause: emails are sent during the request, and the mail library waits up to 2 minutes to connect and 10 minutes per send. During testing, filing a complaint took 75 seconds, and a gift-card booking took more than 5 minutes (the booking was still saved).
   - Fix: mail timeouts are now 10–20 seconds. A mail that times out stays in the outbox and is retried automatically.

New automated checks were added for fixes 1–4 (extra-time, gift-card and settings test suites).

## 5. Improvement suggestions

**High**
- Reliability: send all emails from the background worker instead of during the request (see open issue 4). This keeps booking and complaint screens fast even when mail is slow.
- Security: make the server require an expiry date when verifying ID or permit documents (open issue 1).
- Business: decide how extra time on paid bookings is invoiced (open issue 2), so the accounts match what customers paid.
- Testing: add a small "dev/test" switch to simulate PayPal approval on the local setup (the automated tests already have a fake PayPal). Then the full payment path can be clicked through without a sandbox browser login.

**Medium**
- UX: show "Fee 0 € – cancelled free" vs "Fee 10 €" more prominently. The 24-hour cut-off is exact to the minute, so a customer cancelling right at the edge may be surprised.
- UX: on the earnings page, show the commission-based pay clearly instead of the hourly rate (open issue 5).
- Reliability: fix the "refund pending" status for gift-card bookings (open issue 3).
- Ops: set a separate `INVOICE_EMAIL` in production, so invoices show a proper contact address.

**Low**
- Messages show only the first name (e.g. "QA"). That is fine, but consider "Name (Fiduxa office)" for admin messages.
- The admin can cancel a booking without giving a reason. Consider requiring a short reason for the audit log.

1. **No overlapping jobs for a cleaner.**

## Automatic assignment (round 3)

### What changed

**1. Cleaner availability (before booking)**
- Cleaners manage their availability under *Verfügbarkeit*:
  - **Weekly pattern** (required): working days and hours. Each time range can apply every week, or only to week A or week B (every 2 weeks). Week A/B is counted from Monday 1 Jan 2024, so it never jumps at a year boundary. The page shows which week is the current one.
  - **Monthly calendar**: a single date can be marked "not available", or get extra hours. Holidays stay as before.
  - **Maximum workload**: jobs and hours per day and per week (empty = no limit).
  - **Location**: home postcode plus maximum travel distance in km (default 10).
  - **Skills**: services and extras the cleaner does *not* do (catalogue IDs; ticked = "I do this").
- **A cleaner without a weekly pattern is not available.** The dashboard shows a prompt; it shows another one when the home postcode is missing.
- **Customers only see start times where at least one SUITABLE cleaner is free** for the whole job plus the 30-minute travel buffer. Suitable means: approved and active, not paused, inside the pattern and date overrides, no holiday, pets OK, documents valid on the day, does the service and every extra, inside their travel radius, and their workload limit is not exceeded.
  - The booking wizard now sends the service, extras, postcode and pets to the slot list.
  - The same check runs again inside the day lock when the booking is created, moved or taken back.
  - Bookings without a cleaner (payment holds, needs-attention bookings) are matched to suitable cleaners with a small matching algorithm, so two jobs never count on the same cleaner.
- **The slot cache is cleared on every change to a cleaner.** A Mongoose hook on the user model fires on every write (save and update) and clears the cache: hours, holidays, pause, documents, status, skills and location. This fixes the stale-cache problem when a cleaner is paused or changes holidays or hours.

**2. After payment: automatic assignment** (`services/auto-assign.service.js`, `services/matching.service.js`)
- `confirmBooking()` now assigns the best suitable cleaner straight away. This covers PayPal capture and webhook, a gift card that pays the whole booking, cash and invoice bookings, admin phone bookings, and recurring occurrences. The slot stays held by the reservation from the moment the booking was created.
- **Score (0–100)**: a weighted mean of
  - distance (inside the travel radius)
  - skills (profile specialties that match the service and extras)
  - rating
  - reliability (active strikes plus complaints in the last 180 days)
  - customer preference (plan cleaner or "same cleaner" = 1, a previous cleaner = 0.6)
  - workload balance (hours already booked this week)
- A customer's "different cleaner" choice is used as a **do-not-send** list.
- Recurring occurrences prefer the plan's cleaner whenever that cleaner is suitable.
- **Safety:**
  - A lock per booking (`assign:<id>`) means one assignment run per booking at a time. A booking that already has a cleaner is never assigned again, so capture or webhook retries do nothing (idempotent).
  - The existing lock per cleaner (`worker-schedule:<id>`) re-checks overlaps and workload and writes in one step.
  - The write only succeeds while the booking still has no cleaner, so there is exactly one active cleaner per booking.
  - On a replica set the write and the audit entry run in a MongoDB transaction. On a standalone server (the tests, small installs) the code detects this and falls back to the lock pattern. `ASSIGNMENT_TRANSACTIONS=false` forces the fallback.
  - The assignment is only confirmed (state, e-mails, notice) after the schedule write has succeeded.

**3. Cleaner notification, no accept step**
- The cleaner gets an e-mail at once with the address, time, duration, service, extras, notes and pets.
- The job shows a "New" badge and the dashboard counts new jobs. Opening the job marks it as read.
- In auto mode the job board, accept and decline are hidden; the API answers 409 `ASSIGNMENT_AUTO`.
- **"I can't make it" (emergency):** `POST /worker/jobs/:id/emergency { reason }`, also through the old hand-back button. It is possible until the start, including on the day itself.
  - **No strike** when reported more than `emergencyNoStrikeHours` (24 h) before the start; otherwise 1 strike. It can be switched off completely.
- **Assignment history on the booking** (`assignmentHistory`): assigned, notified, reassigned, emergency, removed, needs attention and customer choice, each with who, role, when, why and the score with its breakdown. Every change is also in the audit log.

**4. Emergency: automatic replacement**
- Triggers:
  - an emergency report
  - admin suspension
  - a complaint "suspend" or "block" (only jobs inside the suspension)
  - an automatic pause after strikes
  - document expiry (jobs after the expiry date)
  - the admin removing the cleaner (Admin → Buchung, or Disposition)
- What happens: the cleaner is taken off the job, excluded for this booking, and the next best cleaner is assigned. The new cleaner is notified, the customer gets a "your cleaner has changed" e-mail, and the previous cleaner (except after an emergency) gets a "job reassigned" e-mail.
- Document expiry no longer only *lists* jobs for reassignment: they are replaced automatically, and the admin e-mail says which ones.

**5. No replacement found**
- A booking is never cancelled silently. It stays `confirmed` with `assignment.state = "needs_attention"` and the main reason (for example `location`, `skills`, `busy`), and the admin gets an e-mail at once.
- The customer gets an e-mail with the next 5 genuinely free times near the original time (3 days before to 10 days after). It links to `/konto/buchungen/<id>/termin-waehlen`, where they can:
  - **pick a time** → the booking is moved and assigned
  - **keep waiting**
  - **cancel free of charge** → full refund through the existing refund flow; the cancel preview shows tier `free_no_cleaner`, fee 0 €
- The background job `assignmentWatch` runs every minute and retries each unassigned booking every `retryMinutes` (10). When a booking is still unassigned `escalateHours` (24 h) before the start, the admin gets one "DRINGEND" (urgent) e-mail.

**6. Admin → Disposition** (`/admin/disposition`, in the bookings group of the menu)
- The page shows:
  - live availability per cleaner and day (day or week view): windows, jobs, free time and why a cleaner is off
  - upcoming assignments
  - unassigned bookings and failed auto-assignments with the reason
  - emergencies and replacements
  - day-offs and holidays
  - conflicts (overlaps, and cleaners who are no longer suitable)
  - cleaners without a pattern
- Per booking:
  - the ranked cleaner list with score and breakdown
  - manual (re)assignment, using the same locks
    - a cleaner who is busy at that time → 409 `WORKER_SCHEDULE_CONFLICT`
    - soft problems (outside the radius, skills, workload) → 409 `ASSIGN_OVERRIDE_REQUIRED`, then the admin can confirm an override
  - re-run the matching, or remove the cleaner
  - the assignment history, the e-mails sent from the outbox for this booking, and the audit entries
- **Einstellungen → Richtlinien → Zuweisung**: mode, the six weights, the emergency strike rule, number of alternatives, retry minutes and escalation hours.

**7. Migration and compatibility**
- `assignmentMode: "auto" | "board"`, default `auto` (`ASSIGNMENT_MODE`, admin setting). `board` brings back the old job board, accept and priority window for a rollback. In board mode an empty weekly pattern still means "always available" and there are no automatic replacements.
- `server/src/scripts/migrate-assignment-2026-11.js` (idempotent, `--dry-run`):
  - the existing weekly hours become the weekly pattern
  - the home postcode comes from the address
  - the travel radius comes from the service districts (10–25 km)
  - services the cleaner does not list in their specialties are excluded
  - It has been run on the dev database: 23 cleaners updated. One approved cleaner account without hours is listed and is not available until they set a pattern. The dev site has bookable slots again.
- `seed-dummy.js` now gives every cleaner a home postcode, a radius (14 km, or 8 km for two cleaners), excluded services and a daily limit for newer cleaners.
- Texts in de/en/pl: worker portal, assignment e-mails, the customer booking page ("Your cleaner"), the payment success page, the FAQ "How is my cleaner chosen?", the "So funktioniert es" page, the cleaner list and the "Reinigungskraft werden" page.

### Decisions made

- **Location model: home postcode + travel radius** (not a list of districts). It is the simplest model that the existing postcode centroids (`data/berlin-postcodes.js`) can check. The existing `serviceAreas` districts stay on the public profile and are only used by the migration to choose the radius.
- **Default weights:** distance 25, rating 20, reliability 20, preference 15, skills 10, workload 10.
- **Emergency strike rule:** no strike when reported more than 24 h before the start (same as `lateReleaseHours`); otherwise 1 strike (`late_release`). It can be changed or switched off.
- **Skills are stored as "does NOT do"**, so existing cleaners do everything until they untick something.
- **Missing home postcode** = not suitable (prompt on the dashboard), because the travel radius cannot be checked.
- A manual admin assignment may override soft rules (radius, skills, workload, working hours, the cleaner being excluded for this booking) after a confirmation. Hard rules always block: busy at that time, paused, inactive, documents, holiday, day off, pets.

## File storage (R2)

Every uploaded file and generated invoice PDF now goes to a **private** Cloudflare R2 bucket instead of MongoDB. MongoDB keeps only the key, content type, size and a sha256.

| What | Key in the bucket | Download route (permission check unchanged) |
|---|---|---|
| Cleaner documents (ID, passport, permit, Gewerbe, other) | `documents/<userId>/<docId>.<ext>` | cleaner: own file; admin: download + preview |
| Complaint photos | `complaints/<complaintId>/<n>.<ext>` | admin only |
| Application CVs | `applications/<appId>/cv.<ext>` | admin only |
| Cleaner profile photos | `avatars/<userId>/<timestamp>.<ext>` | public avatar route (as before) |
| Invoice PDFs | `invoices/<year>/<invoiceNumber>.pdf` | customer: own invoice; admin |
| Outbox attachments | invoice: reference to the invoice key; old mails after migration: `emails/<emailId>/<n>.<ext>` | sent by the outbox job |

- Downloads are streamed through the API after the existing permission check. There are no public or presigned URLs, and the browser never talks to R2, so no CORS rule is needed.
- The yearly § 35a tax statement is still generated on demand for each download and never stored.
- **Fallback:** if the four `S3_*`/`R2_*` variables are empty (or under `NODE_ENV=test`), files are kept in MongoDB as before. If an upload to R2 fails, the file is kept in MongoDB and logged. Records with inline bytes and no key are still served from MongoDB.
- **Validation is unchanged:** type is checked by magic bytes (PDF/JPG/PNG, plus Word for CVs and WebP for avatars), with the same size limits.
- **Deletion:** replacing a rejected document, deleting a pending document, replacing or removing an avatar, deleting an account (documents, avatar, complaint photos), purging applications after 6 months, and losing an invoice-number race all delete the objects. A failed delete is logged and queued in `pendingdeletes`; the housekeeping job (every minute) retries with back-off.
- **Invoices:** a PDF missing from R2 (or a blank pre-fix PDF) is re-rendered from the stored figures with the same number and date, then saved again.
- **Migration:** `node src/scripts/migrate-files-to-r2.js --dry-run` counts the inline files. Without `--dry-run` it uploads each one, checks it with HEAD (size), then sets the key and removes the bytes. It is idempotent, supports `--batch=N` and `--limit=N`, and refuses to run without R2. A dry run on the current dev DB found 0 files in every category. **Run it once on the new Atlas DB after the switch.**
- **Tests:** a new suite `file-storage-r2.e2e.mjs` uses an in-memory fake bucket (`STORAGE_DRIVER=memory`; the harness removes the real R2 variables). The other suites still exercise the MongoDB fallback. A smoke test against the real bucket through the dev API passed (cleaner upload, then admin download, then delete; invoice download; 403/404 checks; test objects and users removed).

- **Results:** 22 e2e suites, 1149 checks (47 of them new); 14 unit tests; tsc and lint clean.

## Resilience (round 4)

Goal: handle no internet, server down and database trouble under load without crashes, double charges or lost input.

**Frontend**
- `lib/api.ts` uses a 20 s timeout (AbortController). It sorts every failure into one of these kinds: `offline`, `network`, `timeout`, `maintenance`, `unavailable` (503 DB_UNAVAILABLE / DB_TIMEOUT / 502 / 504), `busy` (503 SERVER_BUSY / 429), `server` or `client`. The rules are in `lib/api-policy.ts`.
- Automatic retries with backoff happen **only for GETs**. POST, PUT, PATCH and DELETE are never repeated unless the call is marked `idempotent`. So bookings and checkout are never re-sent. The only call marked idempotent is the PayPal capture, which settles at most once on the server.
- `componets/resilience/network-status.tsx` sits in the root layout, so it covers the site, /konto, /worker and /admin. It shows a calm banner in de/en/pl ("You're offline – we'll retry automatically" / "Fiduxa can't be reached …"). When the API reports trouble it polls `/api/v1/ready` with backoff, and on recovery it fires a `fiduxa:recovered` event and refreshes the page. During `MAINTENANCE` it shows a full maintenance screen over the page, except under /admin. The page stays mounted underneath, so no input is lost.
- While offline or while the service is down, the booking "pay" button and the /zahlung pay button are disabled and show an explanation.
- Form drafts: the booking wizard already kept its draft in sessionStorage. The contact, business-request and cleaner-application forms now do too (`hooks/use-draft-state.ts`; the CV file is not saved).
- Error boundaries: `app/error.tsx`, `app/global-error.tsx`, `app/(site)/error.tsx` (this one also covers /konto), `app/admin/error.tsx` and `app/worker/error.tsx`. They show a friendly message with "Try again" and retry automatically when the connection is back. `app/not-found.tsx` already existed.
- Payment safety: if the connection drops during the PayPal return, the page shows "We're checking your payment" and re-calls the capture automatically, plus a "Check status now" button. The capture is idempotent: there is a per-order lock, an already-paid payment returns at once, PayPal-Request-Id is `capture-<order>`, and ORDER_ALREADY_CAPTURED falls back to GET. /zahlung/erfolg keeps polling through transient errors instead of showing a failure.

**Backend**
- Mongo: pool 20, serverSelection 5 s, socket 45 s, maxIdle 60 s, all set by env. Connected, disconnected and reconnected events are logged. At startup the connection is retried with backoff (1 s up to 30 s). The HTTP server listens at once, so `/health` answers 200 while `/ready` answers 503 until Mongo is connected and the settings are loaded.
- Every query and aggregation gets a global `maxTimeMS` (`DB_MAX_TIME_MS`, 15 s). Mongoose buffering is capped at 5 s. Mongo network errors, timeouts and maxTimeMS errors are mapped to 503 `DB_UNAVAILABLE` / `DB_TIMEOUT` with Retry-After, not 500.
- Guards (`src/middleware/resilience.middleware.js`):
  - DB not connected: 503 `DB_UNAVAILABLE` within milliseconds. This includes the Stripe and PayPal webhooks, so the providers retry later.
  - Busy guard: in-flight requests ≥ `BUSY_MAX_INFLIGHT`, or a smoothed event-loop lag (perf_hooks `monitorEventLoopDelay`) above `BUSY_MAX_LAG_MS`, gives 503 `SERVER_BUSY`.
  - `MAINTENANCE_MODE=true` gives 503 `MAINTENANCE`. These stay open: admin and auth routes, the webhooks, `/ready`, and anyone with an admin token (the token now carries a role hint; routes still check the role in the DB).
  - The existing rate limits are unchanged.
- `/health` is liveness: `{ status, db, uptime }`. `/ready` (also at `/api/v1/ready`) is readiness: `{ ready, db: "up"|"down", uptime, maintenance, eventLoopLagMs, inFlight }`. Neither contains secrets.
- Process safety (`src/utils/process-safety.js`): unhandledRejection is logged. uncaughtException is logged and the process exits with 1, so Docker restarts it. SIGTERM/SIGINT stop the jobs, stop accepting connections, let in-flight requests finish, close Mongo, and force an exit after 15 s. HTTP requestTimeout is 60 s, headersTimeout 20 s, keepAlive 65 s.
- Jobs: the scheduler skips its ticks while Mongo is down (logged once) and resumes after reconnect. The worker waits for Mongo instead of crashing and writes a heartbeat file for its Docker healthcheck. Queued e-mails stay in the outbox.
- An admin UI toggle for maintenance was **not** added. The env flag is the switch (see the runbook).

**Infra (Hetzner)**
- Every service has `restart: unless-stopped` and a healthcheck: api on /ready, web on /, worker on its heartbeat, mongo with a mongosh ping, caddy on its admin endpoint. api and worker wait for a healthy mongo.
- Memory limits for a 4 GB server: mongo 1280 MB with the WiredTiger cache at 0.5 GB, api 768 MB, web 512 MB, worker 384 MB, caddy 128 MB. Logs rotate.
- Caddy `handle_errors 502 503 504` serves `deploy/hetzner/errors/503.html`, a branded de/en "We'll be right back" page with status 503 that polls /ready and reloads itself. API paths get a JSON 503 `SERVICE_UNAVAILABLE` instead. The password prompt (401) is not affected.
- `deploy/hetzner/healthcheck.sh` runs from cron every 5 minutes (installed by `server-setup.sh`). After two failures in a row it alerts once via `ALERT_EMAIL` and/or `ALERT_WEBHOOK_URL`, and sends a "back online" message on recovery.
- `docs/TEST_LAUNCH_HETZNER.md` now has three new sections: 8 Monitoring (including UptimeRobot / Better Stack), 9 Backups and restore, and 10 "What to do if the site is down".

**Tests**

  - DB disconnect: API answers 503 in under 500 ms with Retry-After, /ready 503, /health 200, both webhooks 503, jobs skipped. After reconnect everything recovers and sessions still work.
  - Maintenance: customers and public routes get 503, while the admin routes, admin token and admin login still work.
